# 双板实时性阶段记录（2026-09-20）

## 当前正式路径

- 固件：`nuttx_r263_safeenv_livetx_ring_3k.bin`
- COM23：边录边分块编码、发送 token
- COM4：接收 token、分块解码、缓冲 PCM、末块后一次播放
- PC：只转发 token 和记录时间，不进入 PCM/播放链路
- 默认参数：2 秒语音拆成 4 块，每块 500 ms；`JX_LIVE_TX=1`、`JX_BUFFER_PLAY=1`

## 实测

2 秒音频整段基线：

- 编码：约 `2.82 s`
- COM4 整段解码：约 `5.02 s`

500 ms 分块：

- COM23 四块编码：约 `3.18 s`
- COM4 四次解码：约 `4.56 s`
- 末块后一次播放：约 `1.9 s`
- r263 中继实测 `11.76 s` 完成并正常退出（含板卡启动与 PC 握手）

同条件 1 秒质量样本：

- 500 ms 分块 PESQ：`1.779`
- 整段 PESQ：`1.760`
- 500 ms 分块相关度：`0.627`
- 整段相关度：`0.507`

## 已否决

- 1k 模型不是速度方案：实测编码 `1.75 s`、解码 `2.10 s`，比 3k 更慢且质量更低。
- 最近点 GELU 的两个变体（单独分支和默认替换）都在双核路径触发
  NuttX 信号量断言，不能用于正式固件。
- 环形异步播放可以提前首声，但在线播放与解码争用会把 2 秒音频拖到约 3 秒输出，
  因此不作为正式路径。
- 解码尾段 LegacyUnit 跳过：`JX_LEGACY_SKIP=7` 可将单板解码从 `2.08 s` 压到
  `1.38 s`，但 1 秒双板样本 PESQ 从 `1.760` 降到 `1.311`；跳过单个单元也只有
  `1.25~1.32`，质量不合格，正式版本保持 `JX_LEGACY_SKIP=0`。
- 编码首块 `Ci=1->Co=4,k=7` 的权重提升实验没有收益（`1430 -> 1450 ms`，
  属于噪声），已撤回。
- 双板并行半段解码可以跑通：COM4 解码前半段、COM23 解码后半段，PC 仍只转发
  token。但端到端只从约 `15.9 s` 变到 `15.7 s`，且播放拆成两块板各半段，
  听感和同步风险不值得，正式路径仍保持单接收板播放。
- r255 双板流水线解码：COM23 解首块后，COM4 在继续编码的同时自解后续块。
  实测第 2 块后 COM4 卡死，后续块无法发送；该路线已否决。
- COM23 -> COM4 反向角色实测稳定：COM23 负责录音/编码，COM4 负责解码/播放。
  r263 增加 live TX、安全 getenv 包装并关闭无效 DCP 路径后，端到端降到 `11.76 s`。

## 当前瓶颈

3k 单板实测：

- 编码 `1.43 s`，RTF `1.43`
- 解码 `2.07 s`，RTF `2.07`
- 解码中 CNN 占 `1.84 s`

下一步要真正达到 RTF < 1，必须继续降低解码 CNN 的计算/访存：

1. 将跨 block 的激活张量改成 int8 + scale，减少 fp32 读写和重复量化。
2. 对解码尾部高时间分辨率层做寄存器分块/循环交换，降低每元素访存。
3. 如果内核优化仍不足，只能走模型侧：蒸馏更小的解码器或重新训练更轻量的结构。
